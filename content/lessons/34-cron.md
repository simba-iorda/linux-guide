## Зачем это тебе

Бэкап должен делаться каждую ночь, а не когда ты вспомнил. Отчёт — по будням в девять. Проверка диска — каждые пять минут. Заставлять себя делать это руками бессмысленно: для повторяющихся дел в Linux есть **cron** — планировщик, который запускает команды по расписанию, даже когда ты спишь. Это тот самый «будильник для задач», и он работает на любом сервере.

## Как это работает

### Пять звёздочек

Задачи cron описываются одной строкой из пяти полей и команды:

```
┌───────── минута (0–59)
│ ┌─────── час (0–23)
│ │ ┌───── день месяца (1–31)
│ │ │ ┌─── месяц (1–12)
│ │ │ │ ┌─ день недели (0–7, где 0 и 7 — воскресенье)
│ │ │ │ │
* * * * *  команда
```

Звёздочка значит «любое значение». Вот типичные расписания:

| Расписание | Когда |
| --- | --- |
| `*/5 * * * *` | Каждые 5 минут |
| `0 * * * *` | Каждый час, в начале часа |
| `0 3 * * *` | Каждый день в 03:00 |
| `0 9 * * 1-5` | По будням в 09:00 |
| `0 0 1 * *` | Первого числа каждого месяца |
| `@reboot` | При загрузке системы |

### Как управлять

```bash
crontab -e          # редактировать свои задачи
crontab -l          # посмотреть, что уже есть
crontab -r          # 🔴 удалить все задачи (осторожно, без подтверждения!)
```

`crontab -e` открывает твой личный список задач в редакторе. Отдельно есть системные каталоги (`/etc/cron.d/`, `/etc/crontab`) — туда кладут задания администраторы.

### Две ловушки

**Первая: минимальный PATH.** У cron окружение почти пустое. Команда `backup.sh` может не найтись, хотя в твоём терминале она работает. Поэтому в задачах cron **всегда** указывают полные пути:

```bash
0 3 * * * /usr/local/bin/backup.sh >> /var/log/backup.log 2>&1
```

`>> /var/log/backup.log 2>&1` дописывает в лог-файл и обычный вывод, и ошибки — иначе cron попытается «отправить тебе письмо», которого ты не увидишь.

**Вторая: cron не умеет в зависимости и логи.** Если задача должна выполняться только после сети или с ограничением по памяти — посмотри в сторону **systemd-таймеров** (продолжение урока 32): они дают логи в журнале, зависимости и защиту от параллельных запусков.

> 💡 Проверить выражение и не считать звёздочки руками удобно на `crontab.guru`.

## Итог дня

- Ты умеешь читать и составлять cron-строку из пяти полей и понимаешь специальные расписания `@reboot`.
- Ты знаешь команды `crontab -e` / `-l` / `-r`.
- Ты понимаешь ловушку с `PATH` и умеешь перенаправлять вывод задачи в лог.
- Ты знаешь, что для сложных случаев есть systemd-таймеры с логами и зависимостями.

## Домашка

На своей машине:

1. Открой список задач: `crontab -l` (скорее всего, пусто — это нормально).
2. Добавь задачу: `crontab -e` и строка `*/2 * * * * date >> /tmp/cron-test.log`.
3. Подожди пару минут и проверь: `cat /tmp/cron-test.log` — записи должны появляться каждые две минуты.
4. Ошибись нарочно: поменяй `date` на `kuku` и посмотри в журнале, что скажет cron — `journalctl -u cron` (или `-u crond`).
5. Убери тестовую задачу, чтобы не мусорить: `crontab -e`.
6. Вспомни про бэкап: составь (пока на бумаге) строку, которая каждую ночь архивирует твою папку с проектами. Пригодится в следующем уроке.

## <details><summary>🤓 Для любопытных</summary>

- **crontab-выражение «по будням в 9:00»** легко ошибиться: `0 9 * * 1-5` — это дни недели, а `0 9 1-5 * *` — совсем другое (числа месяца).
- Списки и шаги: `0 0,12 * * *` (полдень и полночь), `*/10 8-18 * * 1-5` (каждые 10 минут в рабочее время).
- Системные каталоги: `/etc/cron.d/`, `/etc/cron.{hourly,daily,weekly}`, `/etc/crontab` — там у задач есть поле пользователя.
- `anacron` (Debian) и `Persistent=true` у systemd-таймеров решают проблему «задача пропущена, потому что ноутбук спал».
- Одноразовые задачи: `at 23:00` ветка или `sudo systemd-run --on-active=30m /opt/backup.sh`.
- У пользователя есть `cron.allow` / `cron.deny` — кто вообще имеет право планировать задачи.
</details>
