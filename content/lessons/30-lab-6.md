## Зачем это тебе

Знания из модуля 6 пора собрать в рабочий порядок. Дальше это станет твоей рутиной: «сервер недоступен» → пройти по шагам и найти виновника. Порядок проверок важно не менять: сначала связь, потом имена, потом служба. Если начать с конца, будешь чинить не то.

## Как это работает

Вот сценарий, который встречается чаще всего. Ты получил доступ к мини-серверу, но по адресу ничего не отвечает. Ходи по этажам сверху вниз:

1. **Есть ли связь вообще.** `ping 8.8.8.8` — публичный адрес. Отвечает → сеть и маршруты в порядке.
2. **Работает ли DNS.** `ping google.com` — по имени. Отвечает → имя переводится в адрес; нет → смотри `/etc/resolv.conf`.
3. **Отвечает ли служба.** `curl http://сервер:порт/` — заходит ли приложение. Тут важен именно порт: сервер может быть жив, а веб-сервис лежать.
4. **Что за сервер и что на нём.** Прочитать заметки о хосте (адрес, порты, учётка), заглянуть в логи.

Полезные команды для живого сервера (в симуляторе их нет, дома — сколько угодно):

```bash
ip -br a                 # адреса интерфейсов, кратко
ss -tulpn                # кто слушает какие порты
ping -c 3 8.8.8.8        # связь по IP
dig google.com           # работает ли DNS
curl -v https://host     # весь диалог с сервером по шагам
```

## Итог дня

- Ты умеешь идти по порядку: связь → DNS → служба.
- Ты научился доставать из заметок и логов нужные факты (`cat`, `grep`).
- Ты понимаешь, что «сервер не отвечает» — это не одна проблема, а минимум три разных.
- Ты знаешь, какими командами проверить живой сервер, когда симулятор не нужен.

## Домашка

Проведи настоящую диагностику своей сети или любого доступного сервера:

1. `ip -br a` — есть ли адрес и поднят ли интерфейс.
2. `ping -c 3 192.168.1.1` (адрес твоего роутера) → `ping -c 3 8.8.8.8` → `ping -c 3 google.com`. Где цепочка рвётся?
3. `dig google.com` — какой сервер ответил и за сколько миллисекунд.
4. `curl -v https://example.com` — пройди глазами по шагам: DNS → соединение → TLS → HTTP.
5. Если есть VPS: `ssh user@host`, `ss -tulpn`, `journalctl -p err -b`. Найди, что торчит наружу.

## <details><summary>🤓 Для любопытных</summary>

- **traceroute** и **mtr** показывают маршрут по шагам — где именно «пропадают» пакеты.
- `ss -s` даёт сводку по соединениям; `nc -zv host 22` проверяет конкретный порт.
- `dig +trace google.com` проходит весь путь от корневых серверов — наглядный урок о том, что DNS не один сервер, а дерево.
- Если служба слушает `127.0.0.1:8080`, снаружи она **недоступна** — нужен `0.0.0.0`. Частая причина «у меня работает, у тебя нет».
- Проверяй не только доступность, но и содержимое: `curl -s URL | head` покажет, не отдаёт ли сервер страницу-заглушку или ошибку 502.
</details>
